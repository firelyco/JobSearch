# JobSearch publication rules

Before publishing code or job/fit data, compare the proposed shortlist with the last published `origin/main` snapshot using `node src/validate_shortlist.cjs`. Run it again with `--check-only` after rebasing and before pushing. Publish `docs/shortlist_validation.json` with fit/salary updates; poll updates use `--report=docs/shortlist_validation_poll.json` to avoid concurrent writers conflicting on the audit file.

Do not silently remove a previously reviewed Strong role because an assessment provider/model or context changed. Retain its prior verdict with a visible reassessment label only while the same skill, scoring rules and employer job inputs still match. A newer completed assessment takes precedence. A changed skill or posting requires fresh review; never present a stale result as currently validated.

An unchanged active job losing Strong without a completed replacement or an explicit eligibility reason must block publication. Report source removals, changed employer inputs, changed rules, and completed downgrades separately. Check the actual dashboard under the user's default filters as well as the automated comparison. Counts alone are insufficient.

Keep career fit, salary eligibility, and assessment freshness distinct. Exclude salary only when a published USD annual base maximum is below $250,000. Undisclosed salary stays eligible but unverified.

Assessment cost rules: completed results are reusable across provider/model, worker-count, retry, and transport changes. Assessment identity depends on the fitment skill, candidate evidence, decision rules and substantive job content. Source freshness checks do not themselves authorize another paid AI assessment. Retain completed records when postings leave the feed. Validate old saved citations without AI when migrating legacy cache entries; preserve the original reviewer/model attribution.

Before new paid inference, reserve an attempt in the private database under the semantic job-input identity. At most two automatic attempts are allowed for unchanged inputs, including interrupted runs. Completed or exhausted entries block more paid attempts; only an explicit `--rescore` or changed substantive inputs can authorize another attempt. Backfill continuation must not force rescoring. Test unchanged jobs across repeated runs, model switches, polling timestamp changes, and interrupted-worker retries with model calls forbidden.

Queue priority: validate pending previously Strong roles before unassessed jobs or ordinary date-cohort work, newest first. The Strong refresh queue must include active previously Strong roles outside a frozen backfill cohort; track its progress separately without changing the cohort denominator. Never requeue a current completed assessment or reset an exhausted retry budget just to satisfy this priority. Routine source checks on current ratings follow genuine assessment work.

Assessment cutoff: ignore employer postings before September 15, 2026 (inclusive start). Enforce `config/assessment_queue.json` before all assessment selection, including previously Strong roles, explicit rescoring, benchmarks and backfill priorities. When the employer date is missing/invalid, use first discovery; a recent discovery must never override a valid older employer posting date. Keep existing assessment/application history; this cutoff limits new processing and must not invalidate cached verdicts.
